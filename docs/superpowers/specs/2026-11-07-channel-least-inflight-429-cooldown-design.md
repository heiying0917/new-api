# 渠道选路：同档最少在飞 + 429 冷却 设计

日期：2026-11-07　状态：已与用户确认（1 竞价规则不变；2 同档最少在飞；3 429 冷却默认 5 秒不加倍；不做 RPM 上限 / 满载等待 / Codex 规则调整）

## 背景

场景：50 个并发打到同一渠道（同一 AWS 账号）同一模型，上游按账号×模型限 10 RPM，超出回 429。现状：

- 同档内按权重随机，不看在飞数；Claude Code 亲和会把同一会话的并发全部导向同一渠道（该渠道不限并发时）。
- 重试按「第 N 次重试走第 N 档」（上游 new-api 语义）：有多档时，第一次失败就跳过同档其它渠道直接降档（竞价模式下即更贵的档）。
- 429 不禁用渠道（正确），本请求换渠道重试（最多换 `RateLimitRetryTimes`=5 次），但没有冷却：被限流的渠道下一秒继续接新流量，落到它上面的请求都要先失败一次。
- 并发上限按渠道统计在飞数，不是 RPM。

## 目标

1. 选路按有效优先级从高到低（竞价：成本价 → 渠道优先级；priority 策略：供应商优先级 → 渠道优先级），与现在一致。
2. 同一档内优先选「在飞最少」的渠道。
3. 渠道亲和保留：亲和渠道可用时优先。
4. 上游 429 后该渠道（细到 key）对该模型冷却一段时间，冷却期间新请求和重试都绕开它；重试先找同档其它渠道，同档没有再降档。

## 选路（首次选路与重试统一）

`service.acquireSatisfiedChannel(c, group, model, failed)`：

1. 候选 = 分组 + 模型下全部可调度渠道（`model.GetSatisfiedChannelCandidates`，内存缓存 / DB 两条路径）。
2. 一次批量读取候选的在飞数与冷却状态（Redis 下合并为一次 pipeline）。
3. 分三轮，前一轮选不出才进下一轮：
   - 第 1 轮：排除「本请求失败过」「冷却中」「并发已满」。
   - 第 2 轮：排除「本请求失败过」「并发已满」；允许冷却中的渠道，解冻时间早的优先。
   - 第 3 轮：只排除「并发已满」（失败过的渠道也可再用，与现在「排除后没得选就退回」一致）。
4. 每轮内按档从高到低；档内按负载最低选，负载并列时按权重随机（权重全 0 等概率）；
   占位（`TryAcquireChannelSlot`，原子）失败说明刚被别人占满，记为已满后继续本档，本档选空再降档。
5. 负载 = 在飞数 ÷ 容量。容量 = 渠道并发上限；不限并发的渠道容量取本档内最大的并发上限
   （本档都不限时容量为 1，即直接比在飞数）。
6. 选不出且有渠道因满载被跳过 → `ErrChannelConcurrencyLimited`（不变）。
7. 不再有「第 N 次重试走第 N 档」。`model.GetRandomSatisfiedChannel(Excluding)` 保留（上游函数），转发路径不再调用。
8. auto 分组：外层逐组逻辑不变，组内改用上述选路。

权重语义变化（用户确认「权重只在负载并列时作为随机权重」）：以前同档按权重随机分流，有权重 > 0 的渠道时
权重 0 的渠道永远选不中、80/20 这类比例也按权重生效；现在先比负载，权重 0 的渠道只要负载更低就会被选中，
有负载时流量趋于按在飞数均分。线上渠道权重目前全为 0，不受影响；今后要「软下线」渠道请用禁用或降低优先级。

已知取舍：在飞数是快照，同一时刻（一次 Redis 往返内）的突发请求可能读到相同计数；
并列时随机打散，有上限的渠道仍由原子占位兜底，不会超过上限。

## 渠道亲和

首选渠道「冷却中」与「并发已满」同样处理：本次走正常选路，不清除亲和记录（冷却 / 满载是暂时的）；
改走的渠道成功后亲和按原逻辑改到实际渠道（`switch_on_success`）。

## 429 冷却

- 触发：转发返回上游 429 且不是渠道失效（与限流重试计数同一判定 `isUpstreamRateLimited`；
  "You exceeded your current quota" 这类按关键词禁用的照旧禁用）。
- 粒度：渠道 × key × 模型（请求的模型名，即选路用的模型）。AWS 配额按账号 × 区域 × 模型，
  多 key 渠道里一个区域被限流不影响其它区域。
- 时长：运营设置 `RateLimitCooldownSeconds`，默认 5 秒，0 关闭冷却；固定时长，连续 429 不加倍；
  不读上游 `Retry-After`（AWS SDK 路径拿不到，原生 HTTP 路径目前也不透传）。
- 渠道是否冷却：单 key 渠道 = 该 key 在冷却；多 key 渠道 = 启用中的 key 全部在冷却（已禁用 key 的冷却记录不计入；
  DB 选路的候选不带 key 内容，按冷却数与启用 key 数比较兜底）。读 key 状态表持渠道锁，与自动禁用 / 启用 key 互斥。
- 冷却记录用选路时的模型名（`retryParam.ModelName`），不用会被改写的 `OriginModelName`。
- 多 key 渠道内选 key：跳过冷却中的 key；全部冷却时照常选。
- 存储：Redis 启用时 ZSET `channel_cooldown:{渠道id}:{模型}`，member = key 指纹（sha256 前 16 位十六进制），
  score = 到期毫秒，键 TTL = 冷却时长；跨 Pod 生效。Redis 未启用退回进程内表。Redis 出错按「不冷却」放行。

## 设置

classic「运营设置 → 通用设置」在「限流重试次数」旁新增「限流冷却秒数」。

## 不做

RPM 上限、满载时等待空位、读取 Retry-After、Codex 亲和规则的 skip_retry、任务类转发（Midjourney / 视频等）的 429 冷却标记。

## 测试

- service（内存缓存与 DB 路径）：同档选在飞最少；有上限 / 不限混合时按比例；并列按权重；
  重试先同档后降档；冷却跳过、过期恢复、全部冷却时选最早解冻；多 key 部分冷却仍可选、全部冷却跳过；
  key 选择跳过冷却 key；亲和渠道冷却走正常选路。
- Redis 集成（`CHANNEL_CONCURRENCY_TEST_REDIS`）：冷却写入、跨实例读取、过期。
- 端到端：gin 路由（令牌鉴权 → 选路 → 转发）+ 3 个同档渠道指向本地假上游，其中一个上游超过阈值回 429，
  50 并发全部成功，被限流渠道在冷却期内不再收到请求。
