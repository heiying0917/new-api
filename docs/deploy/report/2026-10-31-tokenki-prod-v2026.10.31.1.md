## 发现（非本次引入，待用户决策）
客户端 429（163）≈ 渠道 429（164）：限流请求基本没有换渠道重试。原因是渠道亲和性规则「claude cli trace」（`^claude-.*$` + `/v1/messages`，按 `metadata.user_id`）配置 `skip_retry_on_failure=true`，规则一命中（无论是否命中缓存）就禁止失败重试，覆盖几乎全部 Claude Code 流量；`shouldRetry` 先判断亲和性，因此本次新增的「渠道失效换渠道重试」对这部分流量同样不生效（自动禁用不受影响）。

**处理（04:38:53，用户选方案 A，管理 API）**：`channel_affinity_setting.rules` 中「claude cli trace」`skip_retry_on_failure` true→false（仅此一处，codex 规则不变；原值备份于本地 `/tmp/tokenki-scrolltest/affinity_rules_backup.json`）。前后各 254s 对比：

| | 改前 | 改后 |
|---|---|---|
| 客户端 200 | 491 | 679（+38%） |
| 客户端 429 | 111 | 10（−91%） |
| 渠道 429（上游尝试） | 137 | 898 |
| /v1/messages 成功耗时 p50 / p90 / p99 | 12.3 / 28.3 / 52.8s | 16.5 / 38.0 / 68.0s |

抽查 12 条请求均跨多个不同渠道重试（如 98→52→73→69…），「避开本次已失败渠道」生效。延迟上升部分来自原先直接 429 的请求现在重试成功被计入；另一部分来自 AWS SDK 默认 retryer 在同一限流渠道内先重试 3 次（含退避，单次失败约 4–5s）——建议后续把 Bedrock 客户端 `RetryMaxAttempts` 设为 1，交由跨渠道重试快速切换。
